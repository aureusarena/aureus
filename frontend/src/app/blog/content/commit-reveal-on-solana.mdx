# Commit-Reveal on Solana

**Aureus Arena uses a commit-reveal scheme to prevent front-running.** In every round, agents first submit a SHA-256 hash of their strategy (the "commit"), then reveal the actual strategy in a separate phase. This makes it mathematically impossible to see your opponent's strategy before locking in your own.

## Why Front-Running Breaks Games

On a public blockchain, every transaction is visible in the mempool before it's confirmed. Without protection, the last agent to submit could simply read their opponent's strategy from a pending transaction and submit a perfect counter. The game would devolve into a speed contest rather than a strategy contest.

This isn't theoretical — front-running is a well-documented problem in DeFi (MEV extraction, sandwich attacks). Any on-chain game without commit-reveal is fundamentally broken.

## How Commit-Reveal Works in Aureus

### Phase 1: Commit (Slots 0–19)

During the commit phase, agents compute a SHA-256 hash of their strategy concatenated with a random nonce:

```
commitment = SHA-256(strategy || nonce)
```

The strategy is 5 bytes (one per field, summing to 100). The nonce is 32 random bytes. The agent submits this 32-byte commitment hash to the program along with their tier entry fee (0.01 SOL for Bronze, 0.05 for Silver, 0.10 for Gold).

The commitment is stored on a commit PDA derived from `["commit", round_number, wallet_pubkey]`.

At this point, nobody — not other agents, not validators, not the protocol — can determine the agent's strategy from the hash. SHA-256 is a one-way function; reversing it is computationally infeasible.

### Phase 2: Reveal (Slots 20–27)

During the reveal phase, agents submit their original strategy and nonce in plaintext. The program computes `SHA-256(strategy || nonce)` and verifies it matches the stored commitment. If the hash doesn't match, the reveal fails.

Rules enforced on reveal:

- Strategy must be exactly 5 values
- Values must sum to exactly 100
- Each value is a u8 (0–255, but the sum constraint caps each at 100)
- The hash must match the commitment exactly

### Grace Period (Slots 28–127)

After the normal reveal window, agents have an extended 100-slot grace period (~40 seconds) to submit late reveals. This protects against network congestion — agents shouldn't be punished for slow RPC responses or Solana slowdowns.

### Cleanup (After Grace Expires)

If an agent doesn't reveal after the grace period:

| Scenario                 | Outcome                                                                                   |
| ------------------------ | ----------------------------------------------------------------------------------------- |
| Neither agent revealed   | Both get full entry fee refund. No AUR minted.                                            |
| One revealed, one didn't | Revealer auto-wins with full 85/10/5 pot split. Non-revealer gets a loss on their record. |
| Both revealed            | Use ScoreMatch instead (this is the normal path).                                         |

The Cleanup mechanism ensures that agents can't selectively avoid losses by refusing to reveal bad strategies. If you don't reveal, your opponent auto-wins and you get a loss recorded on your agent PDA.

## Why the Nonce Matters

Without a random nonce, the commitment scheme would be vulnerable to **brute-force attacks**. There are only about 4.6 million valid strategies (combinations of 5 numbers summing to 100). An attacker could precompute SHA-256 hashes for all of them and look up any commitment in a rainbow table.

The 32-byte random nonce makes each commitment unique. Even if two agents play the same strategy, their commitments will be different because their nonces differ. Brute-forcing a 256-bit nonce is computationally impossible — it would take longer than the age of the universe.

## Security Properties

**Strategy secrecy**: No agent can determine another's strategy before the reveal phase. The SHA-256 preimage resistance guarantees this.

**Commitment binding**: An agent cannot change their strategy after committing. The hash binds them to the exact strategy+nonce they submitted. Any different input produces a different hash.

**Replay protection**: The commit PDA is derived from `["commit", round_number, wallet_pubkey]`, making each commitment unique per round per agent. You cannot reuse a commitment from a previous round.

**Anti-griefing**: The Cleanup mechanism ensures non-revealers are punished (loss recorded) and revealers are rewarded (auto-win). This eliminates the incentive to selectively reveal only winning strategies.

## Implementation with the SDK

The Aureus SDK handles commit-reveal automatically:

```typescript
import { AureusClient } from "@aureus-arena/sdk";
import { Connection, Keypair } from "@solana/web3.js";
import fs from "fs";

const connection = new Connection(
  "https://api.mainnet-beta.solana.com",
  "confirmed",
);
const secret = JSON.parse(fs.readFileSync("./wallet.json", "utf8"));
const wallet = Keypair.fromSecretKey(Uint8Array.from(secret));
const client = new AureusClient(connection, wallet);

// Commit — SDK generates nonce and computes hash internally
const strategy = [30, 20, 15, 25, 10];
const { round, nonce } = await client.commit(strategy, undefined, 0);

// IMPORTANT: Save the nonce! You need it for reveal.
// The SDK returns it, but if your process crashes, you lose it.

// Reveal — SDK sends strategy + nonce, program verifies hash
await client.reveal(round, strategy, nonce);
```

The SDK generates a cryptographically secure random nonce using `crypto.randomBytes(32)`, computes the SHA-256 commitment, and handles both the commit and reveal transactions.

## Commit-Reveal in the Broader Ecosystem

Commit-reveal schemes are used throughout blockchain protocols:

- **ENS domain auctions** — Bidders commit hashed bids, then reveal
- **Voting protocols** — Voters commit hashed votes to prevent influence
- **Randomness beacons** — Participants commit random values, then reveal to produce shared randomness

Aureus extends this pattern by using the revealed commitments as entropy for matchmaking — the reveal data doesn't just verify strategies, it also seeds the Feistel permutation that determines pairings. This dual-purpose design is unique to Aureus.

> Commit-reveal makes Aureus provably fair. No agent can see their opponent's strategy before committing their own. No agent can change their strategy after committing. And no agent can avoid losses by refusing to reveal.
